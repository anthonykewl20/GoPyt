# Pinned build inputs and wheel verification

This increment addresses build-input control and wheel reproducibility in #23.
It does not establish signed release provenance or close the release programme.

## Selected inputs

`requirements/build.txt` pins pip 26.2.1 and setuptools 82.0.1, with SHA-256 hashes
for their published wheels. `pyproject.toml` requires that exact backend version.
`requirements/security.txt` pins the already selected cryptography 50.0.1 extra
and its CPython dependencies cffi 2.1.1 and pycparser 3.0, again with binary-wheel
hashes. No backend test/doc/core extra is installed. CI first uses the bootstrap
pip to install these lists with `--require-hashes --only-binary=:all:`. Subsequent
project and historical-pair builds use `--no-deps --no-build-isolation`, so they
cannot silently resolve another backend or dependency during the build.

The effective job interpreters are CPython 3.11.16 and 3.14.7 from the pinned
python-build-standalone 20260901 release. Exact archive URLs, compressed sizes and
SHA-256 values are in `requirements/python-standalone.json` for Linux x64 and
macOS ARM64/x64. The installer checks size and hash before filtered extraction,
checks the executable's version before adding its directory to `GITHUB_PATH`,
and the next step independently asserts the expected job interpreter version.

This is a separately chosen CI interpreter distribution: GitHub's distribution
manifest lacked a macOS 3.11.15 build, so merely pinning that setup-python version
would not qualify the supported platform. The selected standalone distribution
provides current named patches on both systems. It adds no GoPyT package/runtime
library dependency. Its publisher and release-host trust remain explicit inputs.

The GitHub actions are immutable commits of checkout v7.0.1, setup-python v7.0.0
and upload-artifact v7.0.1; the recorded metadata uses Node 24. Checkout explicitly
disables persisted credentials. Workflows retain `contents: read`, without adding
publish, issue-write or signing permissions. Python 3.14.7 supplied by the pinned
setup action is the bootstrap used to verify/install the job interpreter.

Ubuntu 24.04 and macOS 15 are named runner baselines. Hosted runner image revisions,
kernel/hardware, bootstrap software and GitHub service operation are not immutable
under those labels. Build reports record available image/version/architecture
values and Python/platform identity. This is a declared hosted-CI trust boundary,
not a claim that the whole host or every transitive binary was independently built.

## Reproduction and contents

`tools/reproducible_wheel.py` requires the exact pip/backend versions. It snapshots
packaging inputs, creates two source directories with different paths, source
modification times and Python hash seeds, and builds offline without isolation.
Both builds use the same explicit `SOURCE_DATE_EPOCH`; CI derives it from the
source commit timestamp. The tool requires byte-identical wheel archives.

It also verifies that every packaged runtime file equals its source bytes,
required metadata is present, payload inventory is bounded and contains no extra
runtime code, ZIP entry names are safe and unique, and RECORD covers the inventory
with correct sizes and SHA-256 values. Both archives, build logs, source/file
hashes and environment reports are retained. CI installs and tests the verified
wheel and uses it in the historical upgrade/rollback check.

These checks establish identity and consistency of the generated bytes. They do
not authenticate an arbitrary publisher: a hostile party can replace an artifact
and an unsigned manifest together. Artifact signing, trusted provenance binding,
full bundled-component/license inventory and vulnerability-response/revocation
policy remain required before #23 can close. Host-image changes or ZIP implementation
changes may still require investigation when comparing different environments.

## Reference and update policy

Existing setuptools was selected by the project before this work. Pinning its
version is a build-dependency decision; studying it did not adopt its development
extras. The Leitir reference for setuptools 82.0.1 verified registry sdist checksum
`7d872682c5d01cfde07da7bccc7b65469d3dca203318515ada1de5eda35efbf9` but reported
Git-tree drift and uncertain license routing. Those limitations are retained in
the evidence. `build_meta.py` and the bundled wheel timestamp helper were studied
as references only; no donor code was copied or imported from a reference shelf.
The actual build uses the separately hash-approved PyPI wheel. Package metadata
and bundled licensing still need a complete release inventory review.

Version/hash updates must identify the selected publisher/version, preserve old
input identities and unsuccessful trials, review dependency/permission changes,
then run source checks, wheel reproduction, negative controls, clean installation,
and upgrade/rollback on the supported matrix. Do not replace hashes simply to
silence a mismatch; investigate the artifact and update through review.

The installation controls follow [pip's secure-install guidance](https://pip.pypa.io/en/stable/topics/secure-installs/).
[Retained evidence](../validation/release-inputs/README.md) separates local results,
CI qualification and remaining release gates. Finite tests do not establish
universal correctness, publisher authenticity or an independent security audit.

All workflows force-reinstall the hash-pinned build/security wheels, including already-present versions. The standalone archive includes a portable pip launcher whose bytes differ from its packaged RECORD. An ordinary same-version install leaves that launcher untouched. The initial inventory CI rejected it on all four platform/version combinations; reinstalling the approved wheel regenerates consistent entry points and RECORD metadata. The verifier remains strict; the bootstrap mismatch and failed CI are retained under validation/component-inventory.
